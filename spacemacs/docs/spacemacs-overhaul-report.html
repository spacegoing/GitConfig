Plan and how it went

  1. Develop in a lightweight Linux container against the latest Spacemacs develop branch, with your real repos mounted, Python tooling installed through uv, so nothing touches the Emacs you use every day.
  2. Replicate on the Mac: install Emacs 30 from emacs-plus next to the existing one, clone Spacemacs develop into ~/.emacs.d-next, install the servers with the same uv script, run the same developer session against GUI Emacs.
  3. You flip the switch with scripts/mac-switch.sh once you have read this.

Two things changed along the way. The silex/emacs images are amd64 only, so the container is plain debian:trixie-slim with Debian's Emacs 30.1 (arm64 native, no emulation). And the develop branch moved dotspacemacs-directory into early-init.el, which is why the generated dotfiles come from the develop template rather than from editing the 2017 one.

Design decisions

One dotfile per OS, the symlink stays

You asked to keep ln -s as the way to pick the init file and not to have a unified file. Spacemacs itself has no "per-OS dotfile" switch: it reads exactly one file, $SPACEMACSDIR/init.el (or ~/.spacemacs). So the layout is:

~/.spacemacs.d/
  init.el        -> init.macos.el   (symlink, git-ignored; on Linux: -> init.linux.el)
  init.macos.el                      full dotfile, macOS values
  init.linux.el                      full dotfile, Linux values
  layers/sdev/                       everything that is the same on both

The two files are generated from the same template and the same layer list by a small script, so they differ only in the OS blocks (font sizes and fallbacks, line numbers, undo system, Homebrew PATH, GNU ls dired switches, iCloud org directory). Everything else lives in the sdev layer, which both load. The result is what you had, minus the drift: the shared part cannot diverge because there is one copy of it.

init.el is git-ignored so each machine can point it wherever it wants without producing a diff. The one-time step on a machine is the ln -sfn you already know.

Latest Spacemacs develop, Emacs 30

Spacemacs develop HEAD 88393ec34 (2026-10-20) with Emacs 30 (30.2 on the Mac, 30.1 in Debian 13). Emacs 30 brings native compilation, which makes lsp-mode noticeably faster, at the cost of a one-time compile when a package is first loaded (see caveats). The new Spacemacs also has dotspacemacs-undo-system, so the Mac keeps undo-tree while Linux uses the built-in undo-redo, each chosen in its dotfile.

Python: basedpyright + ruff server, installed with uv

pylsp with jedi indexes the workspace in-process and is what hung on repos of this size. basedpyright is pyright packaged for pip/uv with node bundled, so the same uv tool install basedpyright works on the Mac and in the container. ruff's own language server does lint, format (SPC m = =) and import organisation. lsp-mode runs the two side by side. Type checking is "off" by default so untyped ML code does not light up; one line in local.el raises it. pylsp stays one word away in the dotfile, with its tuning kept.

basedpyright finds the interpreter on its own: the venv activated with SPC m v w, else ./.venv or ./venv in the project (uv convention), else python on PATH. The test repos each had a uv venv at .venv with the project installed, which is the real dev scenario.

Rust: rust-analyzer from rustup

Already in use; now with explicit settings so it watches files itself (lsp-mode's watchers are off), runs cargo check on save and does not format on save.

What was deliberately not changed

Your keys and habits: helm, evil, the SPC h h h highlight, , p header toggle, SPC j M, the dired+ setup, theme tsdh-dark, Source Code Pro 22, TUNA mirrors, the *spacegoing* home buffer. The manual's "what changed" table has the short list of visible differences.

Verification in the container

Container spacemacs-dev: Debian 13 (arm64), Emacs 30.1 (emacs-nox, run as emacs -nw inside tmux), Spacemacs develop 88393ec34, 289 packages installed from the TUNA mirrors, basedpyright 1.40.2, ruff 0.17.2, pylsp 1.15.0 (for the baseline), rust-analyzer from rustup. Repositories were APFS clones of your local vllm, verl and Megatron-LM checkouts with uv venvs created inside the container, plus a small cargo project.

A driver script typed the keys a developer types, through tmux, and measured what Emacs did. In parallel an emacsclient --eval t probe ran three times a second; its round-trip time is how long Emacs was unresponsive at that moment, which is the "freeze" you reported. The session per repo was:

  6. Rust: open main.rs, hover, insert a type error, save, expect rustc's "mismatched types".

Baseline: the same session with the old settings

To quantify what the overhaul removes, the identical driver session was run with a dotfile carrying the pre-overhaul settings: pylsp as the Python server with jedi symbols, pyflakes, pycodestyle and mccabe on, the semantic layer, lsp file watchers on with no threshold, lsp-idle-delay 0.0, code lenses on, workspaces kept alive, and anaconda-mode / importmagic not excluded.

Two baseline runs were made, both on the same Spacemacs develop and Emacs 30.1 as the new config.

Baseline 1: old settings including the semantic layer

lsp-mode never came up. On all three repos the Python buffer opened (1.5 s on vllm), flycheck's own python checker ran, but after 120 s no language server had started and lsp-mode was not even loaded, so there was no hover, no goto definition, no completion from a server, no ruff. , p could not toggle anything. The first start of this dotfile also failed to byte-compile the layer's srefactor package on Emacs 30 ("There should be a mode declaration in .../srecode/c.srt"). The same dotfile loaded in a batch session does load lsp-mode, so the exact interactive failure was not pinned down; what is established is that the semantic layer, as the old config used it, is incompatible with the current Spacemacs and Emacs 30 in practice, and that removing it (which the new config does) makes the difference.

Your part: the final switch

# 1. quit Emacs, then in the live repo
cd ~/.spacemacs.d            # = ~/sg21CodeLab/GitConfig/spacemacs
git status                   # .spacemacs.env* are untracked and ignored on the new branch; fine
git checkout spacemacs-overhaul

# 2. swap ~/.emacs.d for the prepared one and set the symlink
scripts/mac-switch.sh
#    -> ~/.emacs.d            moved to ~/.emacs.d.bak-2026MMDD-HHMM
#    -> ~/.emacs.d-next       becomes ~/.emacs.d   (Spacemacs develop, packages installed)
#    -> init.el               -> init.macos.el
#    prints:  open /opt/homebrew/Cellar/emacs-plus@30/30.2/Emacs.app

# 3. optional: make it the Emacs you launch from Spotlight
ln -s /opt/homebrew/Cellar/emacs-plus@30/30.2/Emacs.app /Applications/Emacs-30.app

# 4. the leaked token: github.com -> Settings -> Developer settings -> Personal access tokens -> revoke

First start takes a little longer than usual while Emacs 30 native-compiles packages in the background the first time they load (magit, rustic, lsp-ui); after that they are instant. The first time you open a file in a repo lsp-mode asks once for the project root: press i. If you jump into a typeshed stub it asks once about that directory: press d.

Rollback

scripts/mac-switch.sh --undo ~/.emacs.d.bak-<date>   # restores the old ~/.emacs.d
cd ~/.spacemacs.d && git checkout master              # old dotfiles and symlink target
# then open the old Emacs app as before

The branch does not delete anything from history and master is untouched, so both setups can coexist until you are happy.

Caveats and things to know

  • One-time native compilation stalls. On the Mac, the first SPC g s took 16 s and the first .rs file 5.5 s because Emacs 30 compiled magit and rustic to native code on first load. This happens once per package version and is the price of the faster steady state. The second Mac run (mac4) shows the warmed numbers.
  • basedpyright on vllm uses real memory. With torch and friends installed in the venv, basedpyright's node process reached about 2 GB RSS while indexing vllm's imports and 110% CPU for a few seconds. Emacs itself stayed responsive; the server is a separate process. It is freed when the last vllm buffer is closed.
  • The "import project root" prompt. lsp-mode asks once per project (answer i) and once for basedpyright's bundled stubs when you jump into one (answer d). The answers are remembered in ~/.emacs.d/.cache/lsp-session-v1.
  • Megatron-LM and ruff. Its pyproject.toml enables only rule S506, so ruff reports almost nothing there by design. basedpyright still reports unused imports and undefined names.
  • Type checking is off. lsp-pyright-type-checking-mode "off" gives the same error classes you had with ruff-only pylsp. Set it to "basic" in local.el when you want type errors.
  • Container vs Mac. Same dotfile layout, same layers, same servers, same uv install path. Differences are only Emacs 30.1 vs 30.2, terminal vs GUI, undo-redo vs undo-tree, line numbers off vs on, chosen per OS in the two dotfiles.
  • Terminal Emacs only: in the container, *Messages* collects "Invalid face reference: lsp-flycheck-info-unnecessary" lines while a Python buffer has diagnostics. It is an lsp-mode/flycheck face missing in a terminal frame, cosmetic, and did not appear in the GUI Emacs on the Mac.
  • The container's goto-definition probe. The driver's own asynchronous textDocument/definition probe never resolved (a harness limitation in how it parsed the result), while the real SPC m g g key worked every time and is what the tables report.

Appendix: how the sessions were driven

Everything lives under the session scratch directory and is not part of the repository.

  • Container driver (repos/_driver/drive.sh + helpers.el): starts emacs -nw with server-start in tmux, sends real key sequences (SPC f f, , g g, , = =, , p, SPC g s, SPC q q) with ESC timing so it is not read as Meta, answers the root prompt, and reads state through emacsclient --eval. lsp requests used for measurement are asynchronous so the probe itself never blocks Emacs.
  • Mac driver (macdrive.sh): starts the emacs-plus GUI with --init-directory ~/.emacs.d-next and SPACEMACSDIR pointing at the worktree dotfile, use-dialog-box nil so any question lands in the minibuffer where a logger records it, then runs the same steps through emacsclient and the real key bindings.
  • Freeze detector: a background loop timing emacsclient --eval t three times a second; every sample is in latency.log, summarised as mean, worst, and counts above 300 ms and 1 s.
  • Repos: APFS clonefile copies of your local vllm, verl and Megatron-LM, with uv venv + uv pip install -e . (dependencies as far as they install offline through the proxy) inside the container and again on the Mac, so basedpyright resolved real site-packages.
  • Baseline dotfile: the Linux dotfile with the old values reinstated (pylsp, semantic layer, watchers, idle 0.0, lenses, keep-alive, nothing excluded), run once through the identical session.

Logs: repos/_logs/run3, run4, baseline, mac-logs/mac3, mac4, each with steps.log, latency.log and the final *Messages* tail.
